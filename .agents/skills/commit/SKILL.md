# Commit

## 절차

### 1. 변경사항 분석

- `git status --short`, `git diff`, `git diff --cached`로 추적 여부와 staged·unstaged 변경을 함께 확인한다.
- untracked 파일은 내용을 확인한 뒤 포함 여부를 판단한다. 비밀 키와 `.env` 등 민감한 파일은 커밋 대상에서 제외한다.
- Git 저장소가 아니면 상황을 알리고 중단한다. 임의로 `git init`하지 않는다. 커밋할 변경이 없으면 이를 알리고 종료한다.

### 2. 논리적 단위 분류

- 기능 추가, 버그 수정, 구조 개선, 유지보수 등 변경 목적에 따라 묶는다. 하나의 목적을 완성하는 변경은 함께 커밋한다.
- 기존 staged 변경도 검토하며, 요청과 무관한 사용자 변경을 임의로 포함하거나 해제하지 않는다.
- 파일 일부만 포함해야 한다면 해당 변경만 스테이징할 수 있도록 준비한다. 이를 안전하게 분리할 수 없다면 사용자에게 범위를 확인한다.

### 3. 한국어 메시지 제안

메시지는 다음 형식을 사용한다. 타입은 영어, 요약은 변경 결과가 드러나는 간결한 한국어로 작성한다.

```text
feat: 알림 설정 패널 추가
fix: 빈 프롬프트의 생성 요청 방지
refactor: 컴포넌트 생성 로직 분리
chore: 개발 도구 설정 정리
```

- `feat`: 새로운 기능이나 사용자 경험 추가
- `fix`: 잘못된 동작 수정
- `refactor`: 동작을 유지하는 내부 구조 개선
- `chore`: 설정, 의존성, 문서 등 유지보수

각 커밋의 대상 파일·변경 요약·메시지와 관련 검증 결과 또는 미실행 사항을 제시한다.

### 4. 승인 후 커밋

- **제안한 커밋 범위와 메시지를 사용자에게 보여주고 명시적 승인을 받은 후에만 `git commit`을 실행한다.** 최초의 '커밋해줘' 요청은 구체적인 제안에 대한 승인으로 간주하지 않는다. 승인 요청 시 이 스킬의 해당 요구사항과 파일 경로를 알린다.
- 승인 후 diff를 다시 확인한다. 승인한 범위나 메시지에 실질적인 변경이 생겼다면 제안을 갱신하고 다시 승인받는다.
- 승인된 변경만 명시적인 경로 또는 필요한 패치 단위로 스테이징하고, `git diff --cached`로 해당 커밋의 내용이 승인 범위와 일치하는지 확인한다. 무조건적인 `git add .`는 사용하지 않는다.
- 논리적 단위별로 커밋한다. 여러 줄 메시지는 임시 UTF-8 파일과 `git commit --file`을 사용한다.
- 실패하면 원인을 설명하고 중단한다. 훅을 우회하거나 커밋을 성공시키려고 무관한 변경을 하지 않는다.
- 완료 후 커밋 해시·메시지와 `git status --short`로 확인한 남은 변경을 보고한다.
- 이 스킬은 로컬 커밋까지만 수행한다. 별도 요청 없이 push, amend, reset 등 원격 반영이나 기록 변경을 하지 않는다.
